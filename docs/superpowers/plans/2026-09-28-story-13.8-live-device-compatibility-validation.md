# Story 13.8 Live-Device Generic Compatibility Validation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce dated physical-device evidence that best-effort compatibility works across representative rendering capabilities and fails safely for unsupported patterns.

**Architecture:** Automated fixture and UI suites establish reproducibility first. A bounded manual matrix then exercises the production Browser → Detection → Reader → View Original Page flow on a physical iPhone. Results are classified by capability and failure type; named domains remain only in internal evidence.

**Tech Stack:** Xcode/iOS UI tests, physical iPhone, Swift Package tests, internal Markdown evidence, sanitized screenshots/logs.

## Global Constraints

- Stories 13.1–13.7 must be complete before device sign-off.
- Select samples for rendering diversity, not domain count or popularity.
- Do not sign in, purchase, bypass challenges, defeat paywalls, or capture protected media.
- Do not claim universal or permanent site support.
- Keep named domains out of the PRD and user-facing product surfaces.
- Do not commit credentials, cookies, personal history, or copyrighted chapter imagery beyond minimal safe evidence.

### Task 1: Create the device-validation protocol and report schema

**Files:**
- Create: `docs/qa_guides/2026-09-28-generic-compatibility-device-validation.md`
- Create: `docs/qa_evidence/2026-09-28-generic-compatibility/report.md`

**Interfaces:**
- Consumes: Story 13.7 capability matrix and current source research catalog.
- Produces: repeatable device steps and a fixed evidence schema.

- [ ] **Step 1: Write the protocol header and prerequisites**

Record app commit, build configuration, device model, iOS version, network type, test date/time zone, tester, and whether the source page was user-opened. Require a clean app launch but do not clear cookies or local data unless that specific state is being tested.

- [ ] **Step 2: Define the per-case record**

Use this exact table schema:

```markdown
| Case | Date | Capability | Internal target | Browser load | Detection/disposition | Reader opened | Image order/load | View Original | Browser state preserved | Classification | Fixture captured | Notes |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
```

Allowed classifications are `pass`, `generic-extractor-gap`, `adapter-opportunity`, `unsupported-by-policy`, and `external-transient`.

- [ ] **Step 3: Define positive-flow steps**

For each eligible long-strip case: open from URL/search, wait for page settle, record disposition, enter Reader automatically or through the offered action, verify first/middle/final image ordering, exercise rapid scroll, verify no canvas flash, open View Original Page, and confirm exact chapter URL/history remains usable.

- [ ] **Step 4: Define negative-flow steps**

For challenge, authentication, paywall, protected/canvas/blob, and paginated cases: confirm Browser remains visible, no unsafe Reader action appears, navigation remains usable, and no bypass attempt is performed.

- [ ] **Step 5: Commit protocol scaffolding**

```bash
git add docs/qa_guides/2026-09-28-generic-compatibility-device-validation.md docs/qa_evidence/2026-09-28-generic-compatibility/report.md
git commit -m "docs: define generic compatibility device validation"
```

### Task 2: Establish automated preflight evidence

- [ ] **Step 1: Run the full Swift package suite**

Expected: zero failures. Record the executed test count and timestamp; do not write “pass” if the command fails.

- [ ] **Step 2: Run the compatibility matrix explicitly**

Run: `cd app && swift test --filter GenericCompatibilityMatrixTests`

Expected: every manifest row passes. Record covered, partial, and unsupported-by-policy counts.

- [ ] **Step 3: Run Browser/Reader UI regression on iPhone 16e simulator**

Expected: zero failed UI tests. Record the `.xcresult` location.

- [ ] **Step 4: Record failures literally**

If any command fails, paste the failing test identifier and concise failure text into the report, classify the release gate as blocked, and stop before live positive claims. Do not paraphrase a failing run as flaky without a reproduced second run and evidence.

- [ ] **Step 1: Select positive cases**

Choose one currently reachable case for each available capability: embedded image metadata, common lazy attributes, hydrated rendered DOM, and browser-session delayed hydration. Prefer neutral/public test content when available. Record selection rationale by capability, not popularity.

### Task 4: Execute positive physical-device flows

**Files:**
- Modify: `docs/qa_evidence/2026-09-28-generic-compatibility/report.md`
- Add when safe: `docs/qa_evidence/2026-09-28-generic-compatibility/*.png`

**Interfaces:**
- Consumes: physical iPhone build and selected positive cases.
- Produces: dated observations and safe screenshots.

- [ ] **Step 1: Build and install the reviewed commit on the physical iPhone**

Use the repository's configured development signing. Record the exact commit and build configuration in the report.

- [ ] **Step 2: Run every positive flow**

Execute the protocol without changing Reader defaults between cases. Record Browser load, disposition, Reader presentation, image count/order, visible loading behavior, View Original Page, and Browser-state restoration.

- [ ] **Step 3: Exercise continuity and zoom on one long chapter**

Rapidly scroll through at least 25 panels, retry one intentionally failed/interrupted page if reproducible, pinch to at least `2x`, reset to `1x`, continue scrolling, and verify progress remains coherent.

- [ ] **Step 4: Capture only safe evidence**

Prefer UI chrome, diagnostics counts, or neutral test fixtures. Crop or omit copyrighted panels, personal history, cookie dialogs containing identifiers, and account information. Reference uncommitted sensitive evidence by location without adding it to git.

- [ ] **Step 5: Classify every result**

Use only the allowed classifications. For `generic-extractor-gap`, record the smallest reproducible DOM characteristic and whether a sanitized fixture can be created. For `external-transient`, record the response/challenge symptom without promising a code fix.

### Task 5: Execute negative flows and issue the release recommendation

**Files:**
- Modify: `docs/qa_evidence/2026-09-28-generic-compatibility/report.md`
- Modify when a safe generic gap exists: `app/Tests/ToonEdgeAppCoreTests/Fixtures/compatibility_matrix.json`
- Add when a safe generic gap exists: `app/Tests/ToonEdgeAppCoreTests/Fixtures/generic_<capability>_regression.json`

**Interfaces:**
- Consumes: selected negative cases and positive results.
- Produces: safe-fallback evidence, regression references, and release recommendation.

- [ ] **Step 1: Run all negative cases**

Confirm Browser-only behavior, absence of unsafe Clean Mode actions, usable navigation, and exact-page preservation. Stop immediately if a flow would require bypassing access controls.

- [ ] **Step 2: Convert reproducible generic gaps into sanitized fixtures**

Add only metadata needed to reproduce extraction/scoring behavior, append an explicit manifest expectation, and run `cd app && swift test --filter GenericCompatibilityMatrixTests`. Expected: the new regression passes after the corresponding in-scope fix; otherwise record the gate as blocked.

- [ ] **Step 3: Write the release recommendation**

Choose exactly one: `ready for best-effort compatibility claim`, `ready with documented limitations`, or `blocked`. Support it with automated results, device cases by capability, unresolved generic gaps, and unsupported-by-policy cases. Include the statement that results are dated observations, not permanent site guarantees.
