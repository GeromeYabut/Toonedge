# Reader Progress Commit Safety Design

Story 13.4 Stage 2B protects automatic reading updates across asynchronous work. A current measured baseline, a visible decoded page, and the correct Reader installation must still be valid at the actual storage commit. Outdated callbacks must neither change the replacement session nor persist progress, recent-reading records, cache metadata, or their derived library effects.

Status: Written specification approved by the user. Approval unlocks executable implementation planning, not implementation, native experimentation, publication, or production adoption. Begin with the [progress gate foundations plan](../plans/2026-10-07-story-13.4-progress-gate-foundations.md); concrete SwiftData and Reader integration remain separate required slices.

## Scope and dependencies

Stage 2A supplies the pure interaction and reconciliation coordinator. Stage 2B adds a feature progress gate, immutable reading-operation inputs, commit-aware persistence interfaces, and controlled integration tests against the actual Reader view model and storage implementations. It does not implement pinch recognizers, a native scroll host, or a replacement Reader UI.

The default production Reader remains unchanged during this slice. The guarded path is explicitly injected into the real view model for controlled tests and later fixture-host integration; it is not a separate toy view model. A missing guarded writer cannot silently fall back to an unguarded write. Production switching requires the later adoption gate.

Dependencies are the [interaction and reconciliation design](2026-10-07-story-13.4-interaction-reconciliation-design.md), its implemented coordinator, and the [native integration design](2026-10-07-story-13.4-native-integration-design.md). Technical ownership follows [Architecture](../../toonedge_architecture_doc.md), product scope follows [PRD](../../toonedge_prd.md), and Reader behavior follows [UX Requirements](../../toonedge_ux_requirements_doc.md).

Stage 2A is merged through [PR 14](https://github.com/GeromeYabut/Toonedge/pull/14). This documentation branch starts from freshly verified origin/main `df8daee899dfb0fa6d43cf4f0f159eb078318ec0`, which retains the reviewed Stage 2A commits. ## Audit findings

At the audited baseline, the production SwiftData repository is main-actor-isolated. Its progress, recent-reading, and cache-metadata methods have asynchronous interfaces but no internal suspension between mutation and synchronous context save. Those methods currently accept no commit authorization. Their scheduling boundary therefore cannot be made safe merely by checking the view model before calling them.

| Entry or effect | Current boundary and gap | Required guarded behavior |
| --- | --- | --- |
| ReaderView visible-page callback | Schedules a task with a selection and pipeline identity | Capture installation and measurement identity at observation time; revalidate when delivered. |
| markImageVisible | Checks the pipeline initially; accepts a readiness Boolean or ready status | Require the current measured selection and an actual decoded image in the current pipeline. A caller Boolean is not proof. |
| markImageReady | Checks visibility and pipeline, then marks the selection recorded before saving | Deduplicate only successfully committed effects; failed or rejected work must remain eligible for a fresh attempt. |
| Readiness subscription | Schedules main-actor tasks and checks the pipeline when they run | Preserve the subscription installation; never create baseline permission from readiness alone. |
| updateProgress | Changes display state, then awaits save, enrichment, recent reading, and cache metadata | Admit one immutable reading operation; check every continuation and each actual commit. |
| restoreProgress | Applies a result after an asynchronous lookup without an installation or interaction check | Apply only to the still-open initial-restore window in its original installation. |
| replaceSession | Awaits stored progress before installing, without a replacement operation identity | Latest accepted replacement wins; late results cannot install an older session. |
| Adjacent navigation | Uses an operation UUID and cancellation checks around awaits | Tie that UUID to installation identity as well, so replacement or suspension retires it. |
| Appearance and disappearance | Recreate or cancel pipelines; already-started reading work is not fenced | Retire authority before cancellation; reopening the same content gets a fresh installation. |
| Metadata enrichment | Fetches asynchronously, then mutates whichever session is current | Fetch using captured input; apply only to the still-authorized operation and installation. |
| Recent reading and recent cache metadata | Separate asynchronous service calls; cache recorded flag is set even after failure | Guard the underlying mutations, not just service forwarding; update success flags only after a successful commit. |

Source paths are `Features/Reader/Views/ReaderView.swift`, `Features/Reader/ViewModels/ReaderViewModel.swift`, `Features/Reader/Loading/ReaderPagePipeline.swift`, `Core/Persistence/Repositories/SwiftDataLibraryRepository.swift`, `Core/Services/Implementations/UserDefaultsReaderProgressRepository.swift`, and `Core/Services/Implementations/CacheLifecycleService.swift`, under `app/Sources/ToonEdgeAppCore/`.

Progress saves update stored page position, last-opened chapter, last-read timestamps, and the planned-to-reading transition. Recent-reading reconciliation also updates saved-series progress. Chapter read state and chapters-read counts are derived from stored progress; the separate recordReadingProgress API can additionally set series completion. The guarded path must preserve existing distinctions, not introduce a new automatic series-completion rule.

DefaultReaderPageAssetLoader reads retained cached assets or fetches image bytes; it does not persist newly fetched bytes. Inspection may continue using the existing bounded pipeline. Recent cache metadata is a reading side effect, distinct from image loading and explicit offline retention.

## Architecture choice

| Approach | Tradeoff |
| --- | --- |
| Shared progress gate and guarded repository commits | Selected. Protects actual writes while preserving prompt progress saving and existing service ownership. |
| Entry checks and cancellation alone | Smaller change, but a queued or cancellation-ignoring operation can still mutate storage after invalidation. Does not meet this design. |
| One bundled transaction after metadata fetching | Groups effects, but delays progress saving behind network metadata. Not selected. |

The feature layer owns eligibility. The persistence layer owns the mutation and save. A narrow shared authorization contract connects them without making repositories understand gestures, SwiftUI views, or geometry calculations. Exact Swift signatures and source registration belong in the executable plan.

| Component | Ownership and responsibility |
| --- | --- |
| Existing interaction coordinator | Pure value state and presentation receipts; no repository permission or async work. |
| Reader progress gate | Main-actor feature component that validates the coordinator, installation, measured selection, pipeline, and operation identity. |
| Immutable reading operation | Captured session metadata, source and series URLs, ordered image payload, normalized page-index progress, event date, and authorization identity. |
| Guarded reading-effects writer | Protocol-backed persistence capability for progress, recent reading, and recent cache metadata; validates immediately before mutation and returns committed, rejected, or failed. |
| ReaderViewModel guarded path | Coordinates reads and metadata fetching, routes authorized effects, and applies only current results. Does not touch persistent models. |
| Later presentation adapter | Supplies authentic measurements and synchronous lifecycle events; owns native rendering, not persistence. |

New feature components belong under `Features/Reader/Interaction/`. Shared authorization and writer contracts belong under `Core/Services/`, and the SwiftData implementation belongs under `Core/Persistence/`. Extend dependency injection without enabling the guarded path on the default Reader yet. Reuse existing persistence business rules through focused synchronous helpers rather than maintaining two independent reconciliation algorithms.

## Eligibility and invalidation

The gate permits an automatic reading operation only when all of these conditions hold together:

- The content session, installation, and page order match the current installed session.
- The interaction coordinator is active, idle, and has a current baseline receipt with actual scale exactly 1 and no pending reconciliation.
- The receipt came from an accepted current measurement, not a requested transform, elapsed time, or guessed scale.
- The selected page has positive-area visibility in the usable viewport, is decoded in the current pipeline, and has current resolved geometry and a usable displayed target.
- Initial restore has resolved or its window has closed through current user interaction; a pending old restore cannot regain authority.
- The reading operation is the latest admitted selection for this installation and has not been retired.

Authorization includes the five Stage 2A token identities, pipeline identity, selected page, and a fresh reading-operation UUID. It is not a reusable canSaveProgress Boolean. The gate retains only bounded current state; it does not accumulate every historical operation. No operation can carry authority across installations, even if the content session UUID and source URL are unchanged.

One main-actor owner serializes coordinator transitions and gate invalidation in the same non-suspending event. A rejected stale or malformed event does not invalidate current valid work; any accepted event that retires the receipt does. This includes gesture start, discrete inspection, Reset, a newer requested geometry revision, failed reconciliation, suspension, replacement, and pipeline replacement or loss of the decoded visible target. A newer baseline reading selection supersedes prior pending reading effects.

Changes in decoded dimensions enter the existing ordered geometry path before a new receipt can authorize progress. Readiness callbacks cannot bypass that path. Ending at 1x does not enable saving until the latest baseline application is acknowledged. Stage 2A end/cancel can accept a semantic transition while returning false because geometry is pending; integration observes resulting state rather than treating false as proof that nothing changed.

## Commit boundary guarantee

Preparation may suspend. The final authorization check, persistent mutation, and synchronous save must share one main-actor turn with no await, task scheduling, callback-driven reentrancy, or network work between them. All relevant invalidation events use that same actor. Calling an existing unguarded async repository method from inside an authorization wrapper is not sufficient.

There are two valid orderings:

1. Invalidation occurs before the commit section: reject without mutating persistent models, cached repository state, or storage, even if the asynchronous operation started earlier.
2. The authorized commit section completes first: retain that valid historical write. Subsequent invalidation blocks all later effects from the operation. No rollback of previously valid reading is implied.

This is not permission for an in-flight write to finish after an already-processed invalidation. The non-suspending commit section prevents that interleaving. If a future store must suspend between authorization and actual persistence, it needs equivalent store-side conditional commit semantics before it can support the guarded capability.

Use a fresh Reader-effect ModelContext on the existing ModelContainer with autosave disabled for each guarded SwiftData effect. On save failure, roll back and discard that isolated context. Never roll back the shared main context or allow failed mutations to leak into a later autosave. The repository already uses a comparable isolated-context pattern for search history; Reader effects need their own scoped implementation and visibility tests.

The UserDefaults progress implementation needs an explicit guarded capability too: prepare encoding before the commit section, then validate and synchronously set the captured key and value. Preserve its current page-index format. Do not claim immediate disk durability beyond UserDefaults guarantees. Controlled test writers may suspend before committing, but their final validation and mutation must run together on the same main actor. Validating there and then awaiting an unconditional actor-backed legacy mock save is not a safe adapter.

CacheLifecycleService may forward a guarded request only if the underlying metadata writer preserves that authorization at its mutation boundary. Its existing unguarded asynchronous forwarding is not a safety adapter. Unsupported writers fail closed on the guarded path; optional, absent metadata services remain explicitly absent rather than successful writes.

Each effect commits independently, preserving the existing sequence rather than creating a cross-service transaction. A valid progress save may remain even if later metadata, recent reading, or cache metadata is rejected or fails. That partial sequence is distinct from stale writes: every effect must independently have current authorization at commit.

## Reading operation flow

1. Accept a current measured visible selection, validate decoded readiness, and capture immutable inputs before the first await. Inspection never changes displayed reading progress.
2. Submit captured progress to the guarded writer immediately; do not wait for metadata networking. Reject stale work at the actual commit section.
3. If still current, fetch series metadata using the captured series URL. After completion, revalidate before modifying current session metadata or producing enriched captured input. Keep metadata-request bookkeeping installation-scoped.
4. Submit recent reading with captured identities, progress, and event date through its guarded commit boundary. A late result must not overwrite a newer selection or make an older chapter appear more recent.
5. Submit recent cache metadata at most once per installation after successful commitment. Never downgrade an explicitly retained chapter to recent retention. Mark the operation recorded only for a committed or successful unchanged result.
6. Publish completion bookkeeping and feedback only if the originating installation and operation are still current. Failed or rejected effects do not poison deduplication and can be retried on a fresh eligible event without a timer.

Current display progress can advance on an admitted baseline measurement without claiming storage success. A storage failure preserves the last saved position and exposes a retryable internal outcome; this slice adds no new error UI. Do not publish successful save state from an attempted write.

Metadata fetching must not serialize later progress saves or let an older fetch rewrite newer page progress. If a metadata fetch is shared within an installation, each consumer still needs fresh authorization; sharing the result does not share commit permission.

## Restore and lifecycle

Capture installation, source URL, replacement operation identity, and restore-window state before stored-progress lookup. A delayed result may apply only to that same current installation and open window. User movement, inspection, suspension, or consumed restore closes the window permanently. A rejected result must not set restore-complete flags for a replacement installation or issue an imperative scroll.

The guarded restore path produces an installation-bound placement decision for the coordinator and later host; it does not reuse ReaderView's unconditional post-await scrollTo. Applying a stored index still requires current geometry and acknowledgement. Default placement with no saved progress also needs acknowledgement before saving.

Replacement invalidates old reading authority immediately when accepted, before awaiting the new chapter's stored progress. Only the latest replacement operation may install its captured session. Failure or cancellation can recover the old visual session only through fresh reconciliation; an old baseline receipt cannot revive. Reopening the same content creates a fresh installation. Suspension retires authority before canceling the pipeline; resume requires current decoded geometry and a newly confirmed baseline.

The guarded controller exposes foreground/background and appear/disappear events for controlled tests and later host wiring. Unit tests establish their contract, not proof that the future native host sends them correctly. Actual background/foreground wiring remains an adoption check.

## Explicit user actions

Save to Library and Retain Offline remain available during inspection and do not require automatic-progress eligibility. Capture their target session and a separate action identity at invocation; an await must not silently retarget the action to a new chapter. A deliberately requested action can finish for its captured original target, but its feedback and saved-state flags cannot mutate a replacement installation.

Shared metadata-fetch helpers must preserve this distinction: an explicit action must not borrow an automatic reading lease, and automatic enrichment must not inherit explicit-action authority. Settings persistence is independent of reading progress and is not blocked by inspection. The current generic cache upsert can replace retained metadata with a recent record; the guarded automatic writer must instead return unchanged for an already-retained record, preserving its stored size, date, and downloaded state. This is a narrow coexistence safeguard for the guarded path, not a change to explicit retention/removal policy or a broad cache refactor.

## Validation and acceptance

Use deterministic continuations, not timing sleeps, to pause immediately before each commit boundary and after every asynchronous read or metadata fetch. Release cancellation-ignoring operations after invalidation. Test through the actual guarded ReaderViewModel path, concrete SwiftData and UserDefaults implementations, and controlled writer spies.

| Scenario | Required evidence |
| --- | --- |
| Started save released after inspection, Reset, suspension, replacement, or newer selection | No rejected-operation storage mutation or derived library change. |
| Valid save completes before invalidation | Saved position remains; later effects from the retired operation do not commit. |
| Late metadata, recent reading, or cache work | No wrong-session enrichment, regressed progress, recent timestamp change, or false success flag. |
| Late restore and competing replacements | Latest installation and user position survive; no stale placement command. |
| Same-content reinstall and old readiness subscription | Old pipeline, measurement, restore, and operation identities are rejected. |
| Ready status without image, edge-only visibility, provisional dimensions, or stale receipt | No admission and no write. |
| End at baseline without acknowledgement and repeated Reset | No permission until the latest matching measured baseline. |
| Genuine baseline recovery and backward scrolling | Fresh updates persist; progress is not permanently disabled or forced to increase. |
| Final-page stale write, including single-page chapter | No rejected transition to read state, chapters-read count, or series-completion effect. |
| Writer failure and retry | Isolated failed changes cannot later autosave; valid retry works and does not erase unrelated pending edits. |
| Successful concrete writer commits | Existing repository snapshots and a reconstructed repository see the same saved state. |
| Retained chapter and explicit actions during inspection | Recent bookkeeping never removes retention; captured actions remain usable and feedback stays installation-scoped. |

Tests must compare stored progress, recent-reading records, cache metadata, last-opened/last-read fields, planned/reading/completed state, chapter read state, and chapters-read counts. Preserve existing business rules; test recordReadingProgress completion behavior separately if that entry point is used by the implementation. Do not add it merely to force completion.

The executable plan must include focused RED/GREEN steps, full SwiftPM regression, real iOS 17 API-floor package compilation, and a proportionate generic Simulator app build. New source registration must be explicit before any Xcode fixture uses the guarded path. Build outputs require freshly verified branch-isolated storage and sanitized evidence. No tests or native acceptance results are claimed by this design document.

## Delivery order and remaining gates

Implement in separate reviewable steps after the plan is approved: shared contracts and gate; concrete commit-aware writers and failure isolation; guarded view-model reading and enrichment; restore/lifecycle and explicit-action protection; then complete integration verification and review. Each step needs focused tests before behavior code. Keep source helpers bounded and avoid unrelated repository refactoring.

Stage 2B is complete only when the guarded real view-model path demonstrates stale rejection at actual commit boundaries and successful resumed baseline saving with the concrete stores. Presentation receipts or a pure gate test alone cannot close it. Repository read visibility and main-thread commit cost must be checked; full-chapter parsing, encoding preparation, image decode, and network work do not belong inside a commit section.

Native host feasibility, authentic measurement provenance, container reuse bounds, the three-operation image pipeline limit, two dedicated current-runtime iPhone simulator checks, actual VoiceOver and system Reduce Motion, and default production wiring remain later gates. No native time budget is allocated here. PR 11 policy adoption and any push, pull request, or merge require their own authorization. The old zoom research worktree remains reference-only.

The canonical PRD still says 1x through 3x and immediate normal scrolling at baseline; the approved sticky interaction permits 0.75x through 3x and requires measured reconciliation. This known conflict must be aligned before production adoption, not silently changed in Stage 2B. iOS 17 runtime coverage remains waived while API compatibility stays at iOS 17. Tablet-sized geometry tests do not establish iPad support.

The approved boundary is guarded commit authorization, independent-effect sequencing, failure isolation, and separate authority for automatic reading versus explicit actions. Each executable slice requires its own plan review before implementation. Foundations alone cannot close Stage 2B.
